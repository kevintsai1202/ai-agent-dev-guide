# Spec contract, component catalog, and registry

> The code in this document is the empirical implementation in **Embabel + Spring AI** (marked "▼ Embabel example"); for the backend-agnostic general contract see the "Backend contract" section in [`../SKILL.md`](../SKILL.md).

## 1. json-render flat element tree spec

The single UI description format shared by backend and frontend. **Not nested JSX, but a flat map**:

```json
{
  "root": "root",
  "elements": {
    "root":  { "type": "Stack",   "props": { "direction": "vertical", "gap": "lg" }, "children": ["title", "table"] },
    "title": { "type": "Heading", "props": { "text": "Customer List", "level": "h2" }, "children": [] },
    "table": { "type": "DataTable", "props": { "columns": ["Customer"], "rows": [] }, "children": [] }
  }
}
```

- The top level has only `root` (the root element key) and `elements` (key → element).
- Every element must contain `type`, `props`, `children` (**`children` is an array of other elements' key strings**, not embedded objects).

The backend only needs to output JSON of this shape (the spec is plain JSON, independent of the backend language). Below is the ▼ Embabel example Java record:

```java
public record DashboardSpec(String root, Map<String, ElementSpec> elements) {
    public record ElementSpec(String type, Map<String, Object> props, List<String> children) {}
}
```

### Common pitfall: the LLM wants to emit `{layout, children}`

The LLM easily produces the "intuitive nested" format `{"layout":"vertical","children":[{"component":...}]}`. Three lines of defense:

1. **Every spec-producing prompt carries strict format rules** (shared `specFormatRules()`).
2. **For true streaming (no schema), add an even stronger `STRICT_FLAT_FORMAT`**: explicitly state "the first character must be `{`", "`layout`/`children` are forbidden as top-level keys", "`component` is forbidden as a key name", with a minimal example.
3. **The format demo at the end of the catalog prompt must also be flat format** — don't let the catalog description contradict the spec rules (in the early POC, `toCatalogPrompt()` left an old `{layout,children}` example behind, and it only avoided breaking because each agent overrode it — a landmine).

## 2. Component catalog ↔ frontend registry: two lists to reconcile

This is the structural weakness of dynamic UI: **"what the LLM can use" and "what the frontend can actually render" are two independent lists**, prone to drift.

| | Stored where | Role |
| --- | --- | --- |
| Component catalog | Backend DB (`component_catalog` table) | `toCatalogPrompt()` reads the DB → generates the LLM system prompt (constraining the LLM to only these components + props) |
| Frontend registry | Frontend code | `defineRegistry(catalog, { components })` → the React components the Renderer actually uses to render |

Flow for adding a component: ① add the definition in the DB (name + description + props schema JSON) ② if shadcn's defaults are insufficient, write a React component ③ add a mapping line to the frontend registry / componentMap.

### Consistency check (strongly recommended)

At startup, fetch `/api/catalog`, compare against the set of registered frontend components, and list the gaps:

```ts
const REGISTERED_COMPONENTS = new Set(Object.keys(registryComponents));
function checkCatalogConsistency() {
  fetch("/api/catalog").then(r => r.json()).then(d => {
    const backend = Object.keys(d?.components ?? {});
    const missing = backend.filter(n => !REGISTERED_COMPONENTS.has(n));
    if (missing.length) console.warn("[catalog] in backend, not implemented in frontend (will become unknown components):", missing);
    else console.info("[catalog] frontend and backend components match ✓ (", backend.length, "total)");
  }).catch(() => {});
}
```

Three layers of defense keep catalog drift from becoming a production incident:

1. **Runtime tolerance**: unknown component → Placeholder (no crash)
2. **Streaming tolerance**: partial spec → sanitize (no crash, see the streaming doc)
3. **Startup detection**: consistency check → console warning (catch gaps early)

## 3. Deterministic rendering vs LLM rendering (key decision)

**Not every spec should be generated by the LLM.** The test is dead simple: **"Is this prop human-readable text, or row-by-row data?"**

| Prop nature | Rendering approach | Reason |
| --- | --- | --- |
| **Data array**: DataTable `rows`, chart `data`, lists, rankings | **Always assembled deterministically into the spec by the backend (Iron Rule)** (▼ Embabel example uses pure Java) | The LLM re-transcribing arrays drops items / breaks them → empty table, empty chart; also slow and tampers |
| Narrative text: summary, risks, recommendations, titles | May go to the LLM | Needs language ability |

### Failure mode: empty table / empty chart (must avoid)

When you let the LLM produce a DataTable, the common result is **headers present, rows empty** — the LLM copies `columns` correctly, but `rows` (a dozen-plus objects) get dropped mid-stream or the JSON breaks, and once the frontend's `sanitizeSpec` cleans up, only an empty array remains. Chart `data` is the same. This is a pitfall actually hit in this project. **The only real fix: rows/data are assembled deterministically by the backend, not via the LLM.**

### Mixed dashboards also use deterministic render (▼ Embabel example: Java)

For a rich dashboard like "metric cards + charts + table + narrative", don't hand the whole thing to the LLM just because there's narrative. The correct split:

1. A prior `@Action` uses the LLM to produce a **structured** analysis (`record { summary, risks, recommendations }`).
2. The terminal render `@Action` is **pure Java**: metric/chart `data` / table `rows` come from deterministic computation, narrative text comes from the previous step's analysis object, assembled together into a flat spec.

```java
// Terminal goal: pure Java render (no Ai), exact numbers, narrative from the LLM analysis
@AchievesGoal(...)
@Action
public DashboardSpec render(OppData data, OppAnalysis analysis) {
    // data.items() → DataTable rows; data.stageDistribution() → BarChart data (all computed in Java)
    // analysis.summary()/hotLeads() → Text/Alert (LLM narrative)
}
```

> When should the whole render go to the LLM? Only when there is "**no data array, pure text layout**" and you want the LLM to freely decide the layout. The moment there's a table or chart, go Java.

The three-step split for a list-type flow — **general skeleton: intent extraction (LLM) → deterministic computation → deterministic spec assembly** (▼ Embabel example implemented with GOAP type-driven routing):

```text
UserInput  → extractListParams → ListQuery   (LLM: extract only intent like sort / count / filter)
ListQuery  → buildList         → ListResult  (Java: deterministic computation, exact numbers)
ListResult → renderList        → DashboardSpec (Java: assembles the flat spec directly, terminal goal)
```

General concept: render is **a pure data-assembly step that calls no LLM**. ▼ Embabel example: `renderList` is a **pure Java `@Action` (no `Ai` parameter)** that news up a `DashboardSpec` directly. GOAP fully accepts a pure-Java action; the terminal goal is still reachable.

> Note on streaming interaction: if the render step is pure Java (pushes no tokens), the Controller's `forwardedCount==0`, so it takes the "send the full spec" chunked-streaming path; the frontend lenient/sanitize handles it just the same, no special case needed.

A small helper for assembling the spec (avoiding `Map.of` not preserving order):

```java
private static Map<String,Object> mapOf(Object... kv) {
    Map<String,Object> m = new LinkedHashMap<>();
    for (int i = 0; i+1 < kv.length; i += 2) m.put((String)kv[i], kv[i+1]);
    return m;
}
```

## 4. Component prop names must align with the real catalog

When assembling the spec deterministically, prop key names must align with the component's real schema, otherwise it renders blank. Common @json-render/shadcn components (verified from dist/catalog):

- `Heading`: `{ text, level: h1|h2|h3|h4 }`
- `Text`: `{ text, variant: body|caption|muted|lead|code }`
- `Stack`: `{ direction: horizontal|vertical, gap: none|sm|md|lg|xl, align, justify }`
- `Badge`: `{ text, variant: default|secondary|destructive|outline }`
- `Alert`: `{ title, message, type: info|success|warning|error }`
- `Progress`: `{ value, max, label }`

For custom components (such as `DataTable`, charts, `MetricCard`), you define the props on both sides — the frontend registry and the backend catalog — and they must match.

## 5. Catalog maintenance page

Build an admin page for the catalog CRUD endpoints (`GET /api/catalog`, `GET /api/catalog/all`, `POST`, `PUT/{name}`, `DELETE/{name}`):

- List **all** components (including disabled → you need an `/all` endpoint, since the default `/api/catalog` only returns enabled ones).
- Flag on each row "whether the frontend has implemented it" (`REGISTERED_COMPONENTS.has(name)`): ⚠️ missing implementations render as unknown components.
- Enable toggle / edit (description, category, props schema JSON, ordering) / add / delete.
- When editing the props schema, `JSON.parse`-validate before submitting.

A single-page app needs no router: a single `view` state (`"dashboard" | "catalog"`) + a top nav button to switch is enough to satisfy "pages + links".
