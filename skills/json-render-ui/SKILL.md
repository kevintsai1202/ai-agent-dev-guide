# json-render-ui (Generative UI — frontend skill for LLM-generated dynamic UI)

Turn "a UI spec generated by an LLM backend" into a dynamic frontend: "user types natural language → backend produces a UI spec → frontend progressively renders a dashboard". This skill focuses on the **frontend/backend UI contract, streaming rendering, observability, and interaction**, and is **backend-framework-agnostic** — the backend only needs to produce the spec shape this skill defines and emit progress/cost events.

> **Backend-agnostic (important)**: the core patterns here (spec contract, SSE, lenient progressive rendering, catalog reconciliation, drill-down) apply to **any LLM backend that can produce a UI spec** (Embabel, LangChain, plain Spring AI, Node, …). Every backend example below is demonstrated with **Embabel + Spring AI** and marked "**▼ Embabel example**"; when switching backends, just rewrite that section against the "Backend contract" below — the frontend needs no change. This skill is installable and usable **on its own** — you do not need the backend skill; any backend meeting the "Backend contract" below works.

## Backend contract (any backend must satisfy these 4 points)

1. **Produce a spec**: the backend's terminal output is a `{root, elements}` flat element-tree JSON (see Iron Rule 1). Data arrays are assembled deterministically by the backend, not via the LLM (Iron Rule 3).
2. **SSE events**: push events such as `status / plan / step / chunk / complete / error` over SSE (the event protocol is in the streaming reference, framework-agnostic).
3. **Step/stage progress**: the backend can emit "the planned list of steps + each step's start/finish" events for the progress panel (Embabel uses GOAP plan/step; other backends map this to their own stage/node concept).
4. **Cost aggregation**: the backend can surface token/cost/call-count at the end (omit the cost panel if unavailable).

Evidence source: the `embabel-json-render` POC (Spring Boot 3.5.x + Embabel 0.4.0 backend / React 19 + @json-render + Vite frontend / OpenAI / SSE). All patterns have run in that project.

> **Embabel backend?** The entry point and router for the whole Embabel skill suite is **`ai-agent-dev-guide`**; for how to write the backend `@Agent`/`@Action`/GOAP, see **`embabel-agent-backend`**. This skill handles the frontend and the UI contract.

## When to use this skill

- When building a dynamic rendering frontend for **any LLM backend** (Embabel, LangChain, plain Spring AI, Node, …) that "generates a UI description via an LLM".
- When you need **SSE streaming** to push agent progress, tokens, and the final spec to the frontend in real time.
- When you want to present **backend step-progress / cost** so viewers understand how the agent works (▼ Embabel example: GOAP plan/step).
- When building a **component catalog**-driven extensible UI, or **click-to-drill-down** interaction.

## Core mental model

```text
user input
  → POST /api/.../generate (SSE)
  → backend opens an SSE connection, runs the LLM flow
        (▼ Embabel example: Controller creates an SseEmitter, runs the agent via Autonomy / AgentInvocation)
  → backend terminal output is a spec (json-render flat element tree)
        (▼ Embabel example: the agent's terminal goal produces a DashboardSpec record)
  → SSE event stream: status / intent / plan / step / chunk / complete / error
  → frontend reads events with fetch + ReadableStream
      → accumulate chunk → lenientParseSpec → sanitizeSpec → progressive setSpec
      → <Renderer spec registry/> renders in real time (unknown component → Placeholder fallback)
```

> In the diagram above, **the frontend half (fetch → lenient → sanitize → Renderer) is entirely backend-agnostic**; only "how the backend runs the flow and produces the spec" varies by framework.

**Three Iron Rules (the essence of this skill):**

1. **The spec is a "flat element tree", not nested JSX**: `{root, elements:{key:{type,props,children}}}`, where `children` is an array of key strings. Every place the backend produces a spec must lock down this shape (see `references/spec-and-catalog.md`).
2. **Streaming must be fault-tolerant**: the LLM emits JSON while you render, so the frontend is always handling "half-finished JSON". Always `lenientParse → sanitize → render`; never let partial data crash (see `references/streaming-and-rendering.md`).
3. **Data arrays are always rendered deterministically (Iron Rule)**: anything that is a "data array" — DataTable `rows`, chart `data`, lists/rankings — **must be assembled into the spec directly by backend code, never generated by the LLM** (whether the backend is Java/Node/Python). The LLM only touches narrative text (summary / risks / recommendations). Reason: when the LLM re-transcribes large arrays it drops items or breaks the streaming JSON, and after the frontend's sanitize you get an **empty table / empty chart** (actually hit in this project); it is also slow and tampers with numbers. Test: **"Is this prop human-readable text, or row-by-row data?" Data → backend assembles it; text → may go to the LLM.** (see "Deterministic vs LLM rendering" in `references/spec-and-catalog.md`)

## Development order

1. **Define the spec contract**: the backend produces the `{root, elements}` shape (▼ Embabel example: a `DashboardSpec(root, elements)` record); the frontend has a matching `Spec` type. Nail down this shape before writing anything else.
2. **Build the component catalog ↔ registry**: the catalog (recommended in a DB) defines "which components + props the LLM may use"; the frontend registry defines "which components can actually be rendered". They are two separate lists — **always run a consistency check** (see `references/spec-and-catalog.md`).
3. **Wire SSE streaming**: the backend opens SSE (▼ Embabel example: `SseEmitter`); the frontend uses `fetch + ReadableStream` (**do not use EventSource — it does not support POST**). Event parsing is in `references/streaming-and-rendering.md`.
4. **Progressive rendering**: write `lenientParseSpec` + `sanitizeSpec`, and on each chunk received try to render the currently-available part.
5. **Observability panel**: push backend step-progress events + cost (cost/tokens/llmCalls) to a fixed frontend panel to show how the backend works (▼ Embabel example: GOAP plan/step events) (see `references/observability-and-interaction.md`).
6. **Drill-down interaction (optional)**: inject `onDrill` via React Context; a component carrying a `drillTemplate` can trigger "regenerate" on click, chaining a multi-level analysis flow.
7. **Catalog maintenance page (optional)**: build an admin page for the catalog CRUD endpoints, flagging gaps where "the backend defines a component the frontend hasn't implemented".

## Hard Rules

- **EventSource is unusable** (no POST body support); always hand-parse SSE with `fetch` + `ReadableStream`.
- **Always assume the spec is half-finished**: always sanitize before rendering (fill in `props:{}`/`children:[]`, filter out child refs pointing to non-existent elements, and don't render if `root` doesn't exist yet).
- **Unknown components must have a fallback** (Placeholder); never crash the whole page.
- **Catalog and registry must be reconciled**: at startup, console-warn the components that "exist in the backend but are missing in the frontend"; missing implementations render as unknown components.
- **Backend step-progress events must be routable to "a specific SSE connection"**: forward the backend's plan/step lifecycle events to the current request's emitter.
  - **▼ Embabel example**: GOAP plan/action events **only go to the "global listener"**, not the per-call `ProcessOptions.withListener` (the latter only gets LLM-nested events). You need a global `@Component` listener + a broker that forwards to the "currently active connection" (details in `embabel-agent-backend` §13).
  - Other backends: forward events to the current connection using that framework's own step/stage event mechanism (how to obtain them depends on the framework's docs; not verified by this skill).
- **Data arrays are always assembled deterministically by the backend into the spec**: DataTable `rows`, chart `data`, lists/rankings are never generated by the LLM (it drops items → empty table, breaks the JSON, tampers with numbers). Make the render step "pure data assembly with no LLM call" (▼ Embabel example: a pure-Java `@Action` without `Ai`; the terminal goal is still reachable). The LLM only handles narrative text. Mixed dashboards (metrics + charts + table + narrative) also run the whole render through deterministic code, with the narrative text carried in from a prior LLM analysis step's structured output.
- When generating code for this project, follow the project's comment-language convention.
- Not done until build has run / it has actually rendered.
